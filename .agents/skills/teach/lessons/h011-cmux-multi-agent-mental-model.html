Harness Engineering · Lesson H011

cmux 多智能体：看见并不等于协同

目标：分清工作区、分栏、智能体与协调者，并能自己组织一次三角色协作
一句话答案
cmux 更像一间有隔断、对讲机和状态灯的作战室。它负责让多个终端和智能体有位置、能通信、可观察；至于谁做什么、结果是否正确、谁来合并，必须由主智能体、外部编排器或你来负责。

先把五个概念拆开

概念实际是什么它不会自动做到什么适合怎么用
工作区
sidebar entry		一组相关分栏的容器不会自动让里面的进程共享记忆一个项目或一个大目标放一个工作区
分栏
pane		同一工作区中的可见区域新分栏不等于新队友主智能体、执行者、测试日志并排看
表面
surface/tab		某个分栏里的终端或浏览器标签隐藏标签仍只是一个独立进程在同一位置切换 shell、浏览器或会话
智能体
agent process		Claude、Codex、Kimi 等实际 CLI 会话同目录不代表共享聊天上下文为每个会话给出明确角色、输入和交付物
协调者
lead/orchestrator		拆任务、派工、收结果、处理依赖的人或程序cmux 布局本身不会代替它Teams 主智能体、OMC，或你本人

真正的协同链路

指令与结果流共享工具与状态
关键判断
如果三个分栏分别手动启动了三个 Claude，它们只是三个独立会话，你就是协调者。如果由 cmux claude-teams 或 cmux codex-teams 启动并由主智能体创建队友，主智能体才是协调者；cmux 把队友映射成原生分栏并转发消息。

分栏和“多导航栏”到底怎么选

同一项目、任务彼此相关放在一个工作区，分成多个 pane。这样能同时看主智能体、执行者和验证者。
不同项目、不同目标放在不同工作区。切换时整个上下文和布局一起切换，减少误操作。
多智能体会改相同文件不要只开多个 pane 共用一个 checkout；给它们独立 Git worktree，再由协调者合并。
任务很短或强依赖只用一个智能体。并行管理成本可能大于节省的时间。

你需要操作的只有三段

1. 开工前
写清一个总目标、成功标准和禁止事项；把任务切成互不踩文件的交付物；指定谁是唯一汇总者。
2. 执行中
看通知和等待输入状态；批准高风险动作；发现两个智能体抢同一文件就暂停其中一个；不要替每个智能体不断改目标。
3. 收尾时
要求测试与证据；让验证者做对抗性审查；只由汇总者整合结果；关闭失效会话，避免旧上下文继续发言。

最小可用编队

一个工作区
├── 左侧：Lead（任务拆解、派工、最后汇总）
├── 右上：Builder（只负责实现）
└── 右下：Verifier（只负责测试和反驳）

人类只给 Lead 总目标；Builder 与 Verifier 收到边界明确的子任务。
三者通过文件、Git diff、测试输出和明确消息共享事实。
快速检查
你在同一目录手动打开三个 Claude 分栏。它们会自动成为一个团队吗？

你下一次可以这样做

选一个能拆成“实现 + 验证”的真实任务，只创建上面的三格编队。先要求 Lead 写出任务表，再允许它派工；最后只接受 Verifier 给出证据后由 Lead 汇总的结果。完成一次，你就会真正感受到“多窗口”和“多智能体系统”的区别。
