Skills vs CLAUDE.md：核心分工

最重要的设计决策：某个内容应该放进 CLAUDE.md 还是做成 Skill？ 答案取决于两件事——使用频率和 token 消耗。

📄 CLAUDE.md（常驻）

~500–2000 tokens

每次会话都加载，无论你做什么

  • 每次都需要的规则
  • 项目基本上下文
  • 语言偏好、编码规范
  • 关键命令和禁止事项

🧩 Skill（按需）

~0 tokens（未触发时）

只在需要时才加载，平时不占 token

  • 偶尔才用的专业流程
  • 有完整步骤的复杂工作流
  • 需要专属参考文档的任务
  • 特定场景的规则集
Token 效率原则
如果你有 10 个专业工作流都塞进 CLAUDE.md，每次对话都浪费 5000+ tokens 加载你永远用不到的内容。 把它们做成 Skills——只有被触发时才消耗 token。

什么时候该做成 Skill

这个内容应该放哪里？
每次对话都需要？
→ CLAUDE.md
比如"用中文回复"、"不加注释"——每次都生效的规则。
特定任务才需要？
→ Skill
比如"代码审查流程"、"部署步骤"——只在做这件事时才需要。

判断清单：

  • 这个工作流有多于 5 个步骤 → 做 Skill
  • 需要专属的参考文档 → 做 Skill
  • 一周用不到 3 次 → 做 Skill
  • 需要执行脚本文件 → 做 Skill
  • 每次对话都会用到 → 放 CLAUDE.md

一个好 SKILL.md 的解剖

以你的 storage-analyzer 为例，它的 frontmatter 触发描述是：

---
name: storage-analyzer
description: >
  macOS / Windows 只读存储分析助手... 务必在以下场景使用：
  用户说"存储分析""磁盘满了""C盘满了"...
---

description 字段是触发的关键——Claude 读它来判断"当前场景是否应该激活这个 Skill"。 写得越具体，自动触发越准确。

Frontmatter 必须
name（Skill 名）+ description（触发条件，这是最重要的字段）
铁律 / 核心规则 推荐
这个 Skill 的绝对约束。比如 storage-analyzer 的"全程只读，禁止 rm"。
执行流程 必须
具体的步骤，Claude 按这个顺序工作。越详细越稳定。
references/ 目录 可选
支撑文档。比如 khazix-writer 的写作方法论、风格样例。
scripts/ 目录 可选
可执行脚本。比如 storage-analyzer 的 scan.py、hv-analysis 的 md_to_pdf.py。

动手：设计你的第一个自定义 Skill

思考你日常工作中有哪些重复的、有多个步骤的任务。以下是一些起点想法：

~/.claude/skills/
├── code-review/       ← 代码审查固定流程
│   └── SKILL.md
├── daily-summary/     ← 每日工作总结生成
│   └── SKILL.md
├── bug-report/        ← 格式化 bug 报告
│   └── SKILL.md
└── release-notes/     ← 从 git log 生成发布说明
    └── SKILL.md

一个最简单的 Skill（写完放到 ~/.claude/skills/code-review/SKILL.md）：

---
name: code-review
description: >
  代码审查专家。当用户说"帮我审查代码"、"review 一下"、
  "看看这段代码有没有问题"、"/code-review" 时触发。
---

# 代码审查

## 审查维度（按优先级）
1. 潜在 Bug：逻辑错误、边界情况、空指针
2. 安全风险：注入、硬编码密钥、权限漏洞
3. 性能：不必要的循环、重复计算、内存泄漏
4. 可读性：命名、函数长度、重复代码

## 输出格式
每个问题：[严重级别] 文件:行号 — 问题描述 → 建议修改

## 规则
- 只指出有把握的问题，不猜测
- 先说最严重的
- 给出具体的修改建议，不只是指出问题
